What Triagle holds, who can see it, and what it can do

Triagle reads the alerts your security tools raise, decides each one by rule, and brings the few that matter to a person. This page says plainly what it is given, where that is kept, who can reach it, and what is not done yet.

What Triagle is given

Alerts from the tools you connectEach alert as the tool wrote it: machine names, account names, addresses and command lines. Triagle is not given raw logs, files, mailboxes or passwords.
What your analysts decideClosures, approvals, the rules they teach, and the spot checks they make.

Where it is kept

Your SIEM stays the recordTriagle never changes or deletes anything in the tool an alert came from. It writes its verdict back beside the alert.
A working queueThe newest alerts and the analysts' decisions, in one file in a storage bucket that belongs to the deployment, encrypted at rest. Older closed alerts roll off.
One deployment for each providerA managed security provider gets its own service, its own storage and its own keys. Nothing is shared between deployments.

Keeping one customer's alerts from another's

{% if customer_keys %} {% else %}{% endif %}
A key for each customerA tool that presents a customer's key can write to that customer's queue and read back that customer's record, and no other. The key decides whose alert it is, not the name the sender wrote.
A key on the way inA tool must present a secret key to send alerts. A deployment that serves several customers gives each one its own key, and the key then decides whose alert it is.
The engine stays inside one customerRelated alerts, sign-in counts, repeats and cases are worked out for one customer at a time.
So does the modelWhat the model is shown about earlier decisions comes from that customer's own analysts only.

Who can see it

Signing inSingle sign-on through your identity provider (OpenID Connect), or a password with a code from an authenticator app. Nobody gets in by having an account elsewhere: an administrator lists each person.
RolesAn analyst can approve and close. A viewer can only read. Roles are checked on the server for every request.
GuessingFive wrong attempts lock the name and the address for five minutes. Sessions end after eight hours.
GuestsA deployment can be opened to read-only guests for a demonstration. That is off unless someone turns it on.

Checking an address

Nothing is sent out to be checkedPublic blocklists of attacking addresses are downloaded into Triagle and searched there. An address from a customer's alert does not leave the deployment to be looked up.
Evidence, not a verdictWhat the lists say is shown to the analyst beside the alert. It does not change the verdict, so a list that changes daily cannot change what Triagle decided.

What the model sees

Verdicts are made without itThe verdict on an alert comes from rules, the same way every time. No model is called to decide.
Writing is where it is usedWhen someone opens an alert, a case, a morning report or a draft message, the text for that item is sent to {% if model_word() == 'Gemini' %}Google's Gemini through Google Cloud{% else %}the model this deployment runs itself, at the address set for it, and to nobody else{% endif %}. No model is called to sort the alerts that nobody opens.
Investigating, inside rulesWhen an analyst asks, the model investigates one alert on its own. It starts from the alert's own record and Triagle's knowledge base, chooses among declared, read-only checks, and is not told the verdict. It cannot close an alert, lower one that was raised on evidence, or run an action. If it disagrees with a closure, the alert goes to a person.
One model service, and no otherA deployment sends its prompts to one model service. If that service is slow or down, nothing is sent to another one: the page says the model did not answer, and the verdict stands.
Masked firstAadhaar numbers, PANs, UPI IDs, phone numbers and email addresses are replaced by placeholders before the text leaves, and put back in the answer. Names and street addresses are not recognised.
Not used for trainingNothing is sent anywhere to train a model. {% if model_word() == 'Gemini' %}Google states that it does not use this data to train its models without permission.{% else %}This deployment uses a model on a server its owner chose, and makes no call to a model anywhere else.{% endif %}
A model of your ownTriagle reaches its model through one setting. Point it at a model inside your own network, anything that speaks the OpenAI chat format, and no prompt goes to Google. The rules that bound the model are code, so they are the same whichever model is used.

What Triagle can do

Nothing by itselfEvery response, such as blocking an address, waits for a named analyst to approve it.
The recordSign-ins, approvals and intake are written to a log in which each line carries a hash of the line before, {% if platform_log %}with a copy in the platform's own log{% else %}so an edited line shows{% endif %}.

How it is built and checked

Tests before every releaseThe software cannot be packaged unless every automated test passes. The tests include who may call each address in the application.
ScanningEvery change is scanned for known weaknesses in the code and in the libraries it uses.
In the browserPages run only Triagle's own scripts, cannot be framed by another site, and cannot post a form to another site.
On the server{% if unprivileged %}The application runs as an unprivileged user and holds one narrow cloud role.{% else %}The application holds one narrow cloud role.{% endif %}

Not done yet

An independent penetration testPlanned before the first customer pilot. Until then the checks above are our own.
A certificate such as ISO 27001 or SOC 2None yet.
A login for a provider's own customersToday a provider's analysts sign in. A customer receives its reports from them.
